```
to WSL2: The system cannot find the path specified.
Error code: Wsl/Service/CreateInstance/MountDisk/HCS/ERROR_PATH_NOT_FOUND
```

**Reading the error:** the error code reads from general to specific, like a
traceback. `Wsl` (the product) → `Service` (WSL's background service) →
`CreateInstance` (starting the Linux VM) → `MountDisk` (plugging in its
virtual disk) → `HCS` (Host Compute Service, the Windows component that runs
VMs) → `ERROR_PATH_NOT_FOUND` (the actual cause: the file isn't there).
`ext4.vhdx` = one Windows file containing an entire Linux disk (vhdx = virtual
hard disk format; ext4 = the Linux file-system format inside it).

**Diagnosis, step by step (all read-only):**

1. `Test-Path` on the disk's folder → `False`.
2. Parent folder `C:\Users\chira\AppData\Local\wsl` → does not exist at all.
3. Registry `HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss` (WSL's own
   list of distros) → still lists `Ubuntu` with BasePath pointing at that
   missing folder. `docker-desktop` points at `AppData\Local\Docker\wsl\main`.
4. Searched all of `AppData\Local` for any `ext4.vhdx` → only Docker's
   (0.09 GB). No Ubuntu disk anywhere. No Ubuntu Store package folder either.
5. `wsl --version` → WSL 2.7.11.0, kernel 6.18.33.2-2, Windows 10.0.26100.9457.

**Root cause:** Ubuntu's registration survived but its disk file was deleted
(cause unknown; asked Chirag). It's a **dangling pointer**: the entry exists,
the thing it points to doesn't. `wsl --list` reported Ubuntu as fine because
it reads only the registry and never checks the disk. **Lesson: "listed" ≠
"works". Only actually starting it proves it.** My earlier "No install
needed" was wrong for this reason. I trusted a status report instead of a
test.

Any files that were inside the old Ubuntu are gone and cannot be recovered

Concept summary (for revision): **Git** records snapshots (**commits**) of
chosen files. Each commit is identified by a **hash**, a 40-hex-digit
fingerprint computed from its content and its parent commit, so history
can't be silently altered. Work flows through three places: the **working
folder** (what you edit) → the **staging area** (`git add`: what goes into
the next snapshot) → the **repository** (`git commit`: the permanent
record, in `.git/`). A **remote** is a copy of the repository somewhere else
(GitHub); `git push` sends new commits to it. Analogy: ECO/tape-out
snapshots with a change log; staging = choosing which cells go into this
revision.
